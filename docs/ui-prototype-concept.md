# Web / スマホ UIプロトタイプ構想

## 1. 目的
本書は、現在の予測投票ゲームMVPをもとに、**Web** と **スマホアプリ** の両方で使いやすい UI プロトタイプの方向性を整理するための構想メモです。

狙いは以下です。
- MVPで動いている主要導線を、迷いにくい画面体験へ整理する
- Web とスマホで共通コンセプトを保ちつつ、利用シーンに応じて最適化する
- 次の実装フェーズで「どの画面を、どの順番で、どこまで作り込むか」を判断しやすくする

---

## 2. 前提と設計スタンス
現時点のプロダクトでは、以下の主要導線がすでに存在します。
- Onboarding / Login
- Home
- Event List / Event Detail / Vote
- Vote History / Result
- Avatar
- My Page
- Admin

UIプロトタイプでは、これらの導線を壊さずに以下の方針で再設計します。
1. **最短で投票できること** を最優先にする
2. 結果通知・履歴・アバター成長など、継続利用の動機を見せる
3. Web は一覧性と管理効率、スマホは片手操作と短時間利用を優先する
4. Admin は一般ユーザー導線と分けて、誤操作しにくい構造にする

---

## 3. 想定ユーザー

### 3.1 一般ユーザー
- 通勤中や休憩中に数分でイベントを確認したい
- 参加中イベントの締切や結果だけ素早く知りたい
- 勝敗やポイント、アバター育成の進捗を楽しみたい

### 3.2 管理ユーザー
- Web から複数イベントを一覧で見たい
- 未精算イベントを素早く見つけて結果登録したい
- メトリクスや登録ユーザーの状況もまとめて確認したい

---

## 4. 共通UXコンセプト

### 4.1 体験の中心
アプリ全体の中心体験は、以下の 3 ステップです。
1. **見つける**: 興味あるイベントを探す
2. **参加する**: 迷わず投票する
3. **振り返る**: 結果通知・履歴・成長を確認する

### 4.2 共通デザイン原則
- **1画面1目的**: 1つの画面に複数の主目的を詰め込みすぎない
- **重要情報を先頭へ**: 締切、ベット額、現在の自分の状態をファーストビューに置く
- **状態変化を可視化**: open / closed / settled を色とラベルで判別しやすくする
- **継続動機の演出**: 的中通知、連勝、保有ポイント、アバター成長を継続的に見せる
- **誤操作防止**: 投票確定や結果登録は確認ステップを入れる

---

## 5. 情報設計（IA）案

### 5.1 スマホ
下部タブを中心に、短時間操作向けの構成にします。

- Home
- Events
- History
- Avatar
- My Page
- Admin（admin のみ表示、通常は非表示または導線分離）

### 5.2 Web
Web は左サイドバー + 上部ヘッダーを基本にします。

- Dashboard
- Events
- Results
- Users / Profile
- Avatar
- Admin Console

### 5.3 共通ショートカット
両プラットフォーム共通で、以下のクイック導線を常設します。
- 締切間近イベントへ移動
- 自分の投票履歴へ移動
- 最新の結果通知へ移動
- Admin では「未精算イベント」へ直接移動

---

## 6. スマホUIプロトタイプ構想

### 6.1 全体トーン
- 片手操作しやすい縦長レイアウト
- カードベースの情報整理
- 操作ボタンは画面下部寄りに寄せる
- 主要CTAは 1 画面に 1 つへ絞る

### 6.2 Home
**役割**: 再訪時に「今やること」が一目でわかる画面。

表示優先度:
1. ユーザーサマリー（ポイント、レベル、連勝など）
2. 締切間近イベント
3. あなた向けおすすめイベント
4. 直近の結果通知
5. 確定済みイベントの抜粋

画面イメージ:
```txt
[Header]
こんにちは、DemoUser
1200pt / Lv.4 / 3連勝

[締切間近]
- あと 12分: ○○の勝者は？
- あと 28分: △△の指数は？

[おすすめイベント]
[カード][カード]

[結果通知]
- 的中！ +100pt
- 不的中でした
```

### 6.3 Events一覧
**役割**: 探す・比較する・参加する。

主なUI要素:
- 上部検索バー
- ステータスフィルタ（open / closed / settled）
- カテゴリフィルタ
- eventType（global / local）切替
- イベントカードの情報圧縮表示

イベントカードに載せる情報:
- タイトル
- カテゴリ
- 締切までの残り時間
- 参加人数
- 最低ベット
- 自分が投票済みかどうか

### 6.4 Event Detail / Vote
**役割**: 投票判断を支援し、迷わず確定させる。

構成:
- 上部: イベント概要、締切、カテゴリ、参加人数
- 中央: 選択肢カード
- 下部: ベット入力、消費ポイント、確認ボタン
- 最下部固定CTA: 「この内容で投票する」

改善ポイント:
- 選択肢を選ぶとカードが強調される
- ベット変更時に「実消費ポイント」が即時更新される
- 確定前に確認シートを出し、誤投票を減らす

### 6.5 Vote Complete
**役割**: 投票完了後に次の行動を促す。

表示案:
- 投票完了メッセージ
- 投票内容の要約
- 次の導線ボタン
  - Homeへ戻る
  - 履歴を見る
  - 似たイベントを見る

### 6.6 History / Results
**役割**: 自分の過去行動と結果を振り返る。

構成案:
- タブ切替: 「参加履歴」「結果」
- 勝敗ラベルを色分け
- 各行に報酬ポイントと正解選択肢を表示
- フィルタ: 的中のみ / 不的中のみ / 期間別

### 6.7 Avatar
**役割**: 成長要素を明確に見せる。

表示案:
- アバター本体の大きめ表示
- レベル / 経験値 / パッシブ効果
- 所持アイテム一覧
- レベルアップCTA

体験改善:
- 成長前後の差分を表示
- 「次レベルで何が上がるか」を見せる

### 6.8 My Page
**役割**: 自分の実績の見える化。

表示案:
- プロフィール
- 総ポイント
- 総投票数
- 的中率
- 連勝記録
- 地域設定
- ログアウト / 認証状態表示

### 6.9 Admin（スマホ）
スマホの Admin は **簡易操作版** に寄せます。

優先機能:
- 未精算イベント確認
- 正解登録
- 直近の結果登録結果確認

スマホでは入力負荷が高いため、イベント作成や大規模一覧確認は Web を主運用にします。

## 7. Web UIプロトタイプ構想

### 7.1 全体方針
Web は **一覧性・情報量・管理効率** を重視します。

レイアウト案:
- 左: サイドバー
- 上: ページタイトル / パンくず / ユーザー情報
- 中央: メインコンテンツ
- 右: 補助パネル（任意、詳細や通知）

### 7.2 Dashboard
**役割**: ログイン直後に全体状況を把握する。

表示ブロック案:
- KPIカード（ポイント、参加中イベント、今日締切、直近の的中数）
- おすすめイベント
- 最近の結果通知
- 参加中イベントのステータス
- Admin 権限がある場合は Admin Summary を追加

### 7.3 Events一覧
Web ではカード一覧よりも、**テーブル + 補助カード** のハイブリッドが有効です。

表示項目:
- タイトル
- カテゴリ
- type
- status
- voteEndAt
- participantCount
- minBetPoints
- 自分の投票有無

操作:
- 行クリックで右側パネルに詳細表示
- フィルタを上部に横並び配置
- 締切順 / 人気順 / 新着順ソート

### 7.4 Event Detail
Webでは 2カラム構成にします。

左カラム:
- イベント詳細
- 選択肢
- 参加状況

右カラム:
- 投票パネル
- 自分の残ポイント
- リスク/報酬要約
- 関連イベント

### 7.5 Results / History
Web では分析的に振り返りやすい画面にします。

表示案:
- 的中率サマリー
- 勝敗推移ミニチャート
- テーブル一覧
- フィルタ（カテゴリ、期間、結果種別）

### 7.6 Admin Console
Web Admin は最も作り込み効果が高い領域です。

主なブロック:
- Overview cards
  - open events
  - pending settle events
  - settled today
  - registered users
- Pending settlement table
- Event creation form
- Registered users table
- Metrics panel
- Audit / warnings area（将来拡張）

理想の操作フロー:
1. 未精算イベント一覧を開く
2. 行を選択する
3. 右パネルで正解選択肢を確認する
4. 登録前モーダルで最終確認する
5. 結果サマリーを表示する

### 7.7 Web特有の追加要素
- URL共有しやすい詳細画面
- パンくず
- テーブルの一括絞り込み
- hover / tooltip による補足情報
- 将来的な監査ログ画面

## 8. デザインシステムのたたき台

### 8.1 トーン
- ベース: ダークネイビー系
- アクセント: ブルー
- 勝ち: グリーン
- 注意: イエロー
- エラー: レッド

### 8.2 コンポーネント優先作成順
1. App Shell（ヘッダー、サイドバー、下部タブ）
2. Event Card
3. Status Chip
4. KPI Card
5. Filter Bar
6. Vote Panel
7. Result Row
8. Admin Table
9. Confirm Modal

### 8.3 ステータス表現
- `open`: 青 or 緑系
- `closed`: グレー or アンバー
- `settled`: パープル or ブルーグレー
- `won`: グリーン強調
- `lost`: レッド系だが強すぎない色

## 9. プロトタイプ作成の進め方

### Phase 1: 低忠実度（Lo-Fi）
- まずは画面遷移と情報優先順位を確認する
- Figma で白黒ワイヤーを作る
- 対象画面:
  - Home
  - Events一覧
  - Event Detail / Vote
  - Results
  - Web Admin Console

### Phase 2: 中忠実度（Mid-Fi）
- 色、余白、カード構造、ボタン階層を定義する
- スマホ/Web の差分を比較する
- コンポーネント分解を開始する

### Phase 3: 高忠実度（Hi-Fi）
- 実装に近い見た目にする
- 通知、ローディング、エラー、空状態も追加する
- 実装チケットへ分解できる粒度まで詰める

---

## 10. 実装優先順位の提案
1. **Home 改善**
   - 再訪価値が高く、通知・締切・おすすめをまとめて見せられる
2. **Events一覧 + Detail/Vote 改善**
   - コア体験そのものなので、離脱率に直結する
3. **Web Admin Console 改善**
   - 運用効率と誤操作防止に効果が大きい
4. **Results / History 改善**
   - 継続利用と納得感につながる
5. **Avatar / My Page 強化**
   - リテンション向上に効く

---

## 11. ユーザーテストで確認したい観点
- Home を開いた瞬間に「次に何をすべきか」が分かるか
- イベント一覧から投票完了まで 30〜60 秒で到達できるか
- 締切や状態ラベルを誤認しないか
- 結果通知を見て、履歴へ自然に移動できるか
- Admin が Web で未精算イベントを素早く処理できるか

---

## 12. ひとことで言うと
- **スマホ** は「短時間で参加・確認できるゲーム体験」
- **Web** は「一覧性と運用効率の高いダッシュボード体験」

この方針で進めると、現在の MVP 実装を活かしつつ、ユーザー向け体験と Admin 運用体験の両方を段階的に強化しやすくなります。
